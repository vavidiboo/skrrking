# Skull King Implementation Plan

작성일: 2026-04-06

## 목표
- 기존 프론트엔드 상태관리 방식과 백엔드 계층 구조를 유지한다.
- 스컬킹 규칙 반영은 기존 코드와 충돌하지 않는 최소 수정으로 진행한다.
- 매 작업은 계획 -> 구현 -> 검증 -> 기록 순서를 따른다.

## 작업 원칙
- 규칙 판정은 가능하면 `core` 모듈에 둔다.
- `api_server.py`에서는 세션 변환, 응답 스키마, 인증/운영 정책만 맞춘다.
- `app/app.js`는 기존 `appState -> deriveUiModel -> render` 흐름을 유지한다.
- 에러 메시지는 기존처럼 `HTTPException(detail=...)` 기반을 유지한다.
- 새 타입/필드는 기존 payload 구조를 최대 재사용한다.

## 증분 작업 절차

### 1. 분석
- 관련 파일 검색
- 유사 책임 파일 확인
- 현재 DTO, 상태 필드, 렌더 진입점, 테스트 유무 확인

### 2. 설계
- 확인된 사실과 가설을 분리 기록
- 변경 범위를 `core`, `api_server`, `app` 중 어디까지인지 확정
- 신규 파일이 정말 필요한지 검토

### 3. 구현
- 규칙 로직부터 수정
- 세션/응답 직렬화 경로 수정
- 마지막에 UI 반영

### 4. 검증
- 기존 테스트 실행
- 변경된 규칙에 대한 직접 테스트 추가
- 가능하면 수동 검증 시나리오를 짧게 재현

### 5. 기록
- 무엇을 바꿨는지
- 왜 바꿨는지
- 남은 위험요소
- 실제 실행한 검증 결과

## 다음 기능 작업 시 권장 체크포인트
- 카드 종류가 늘어나는가
- 트릭 판정 우선순위가 바뀌는가
- follow-suit 규칙에 영향이 있는가
- timeout auto-play 정책도 바뀌어야 하는가
- score_breakdown 또는 UI 요약 문구에 새 정보가 필요한가
- spectator/read-only 상태에서도 문제없이 보이는가

## 우선 추천 작업 순서
1. 룰 단위 테스트 기반 추가
2. README와 코드 상태 불일치 정리
3. 남은 Advanced 룰을 하나씩 최소 단위로 반영
4. 각 규칙마다 서버 상태와 UI 노출을 연결
